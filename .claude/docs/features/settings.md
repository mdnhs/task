# Settings, account, audit and search (M0 tenant administration)

Built on the real API in B6 T6.5. Tenant-default notification settings, the delivery log and the report template tab are still mock and show only on a demo deployment (`ENABLE_MOCK_MODULES=1`).

## What the UI no longer offers, and why
| Removed or changed | Why |
|---|---|
| Weekend and holiday rule | The API has public holidays instead (`/v1/settings/holidays`); no rule setting exists. |
| Department sites | Move to rosters (M1A). |
| Department report owner, deactivate department | Report ownership is B8; teams have no active flag. |
| Appearance presets (corners, text, spacing) | No backend field; the brand colour is kept. |

| Built-in roles in the matrix | Read-only in the API (409 `template_locked`). "Copy role" makes an editable copy. |

## WhatsApp notifications (FE-only MOCK, demo flag `ENABLE_MOCK_MODULES=1`)
Outbound only: OpsDesk sends a notification to a person's own WhatsApp for the events in their scope. The backend does not exist yet; everything below is mock JSON (`public/data/whatsapp/*.json`, read by `features/whatsapp/api.ts`) plus local client state (`features/whatsapp/store.ts`, `lib/wa-staged.ts`): nothing is persisted, no network call, no secret. Data shapes: `features/whatsapp/types.ts` (the later API should match them). With the flag off none of it renders, there is no route and no nav or search entry.
- **Settings -> Integrations**: a WhatsApp card next to Google Drive (same structure). Not connected -> Turn on (dialog: verified business number, people opt in, approved templates; steps Not connected, Connecting, Active) -> Active (sending number, today's sent/delivered/failed, Manage). The header counter reads `N of 2 connected`. A plan without WhatsApp disables Turn on and shows an upgrade hint.
- **`/settings/integrations/whatsapp`** (mock route in `lib/mock-registry.ts`, behind `mockGate`): sections as a `FilterSeg`: What gets sent (per notification kind a "Send via" choice: Email only, WhatsApp only, Email + WhatsApp, WhatsApp first then email if not delivered; a tenant-wide default; "Both" is always allowed; plan note with a `.progress` usage bar, e.g. "Plan: 1,000 WhatsApp messages per month, 312 used"), People (status No number / Pending confirmation / Verified / Opted out, scope, last 3 digits only, last message, Edit), Message log (status chips, template, never a body or a full number), Templates (read-only status).
- **Settings -> Users**: the invite dialog has an optional WhatsApp number (country code, Ireland +353 default, E.164 check). The owner's number is only STAGED: "Pending confirmation" in the Users and People lists until the person ticks the opt-in and verifies the code in Account -> Notifications (their screen shows the number pre-filled with the opt-in sentence, checkbox, Send code and the code input). Editing or clearing it is allowed; changing a verified number resets it to Pending confirmation. Nothing is sent before that.
- **Account -> Notifications**: a WhatsApp section: phone with country selector, consent checkbox that gates Send code, 6-digit code with a resend timer, masked verified number with Remove number, per-kind In-app / Email / WhatsApp switches for the kinds the owner sends on WhatsApp (a person may turn a kind off but cannot turn on a channel the owner switched off), "Reply STOP to opt out anytime" always visible, and a short explanation instead of the form while the admin has not turned WhatsApp on.
- Shared pieces: `lib/phone.ts` (pure phone rules and masking), `lib/wa-status.ts`, `components/phone-field.tsx`, `components/wa-number-dialog.tsx`. Icon: `bubble-chat` (the free Hugeicons pack has no WhatsApp glyph).

## Branding (brand colour and neutral tint)
`lib/brand.ts` `brandCss()` is the single source, rendered server-side in `app/(app)/layout.tsx` (no flash) and re-run by the Branding live preview. Besides the accent tokens it now tints the neutral surface scale (`--page --shell --panel --card --ink --ink-2 --ink-3 --placeholder --line --mute-bg --shadow`, light and dark; `lib/brand-neutrals.ts`): each neutral keeps its exact luminance (contrast unchanged), takes the brand hue (its offset from the default hue kept) and its own small chroma scaled by the brand's chroma (greys give greys, loud brands are capped). The default green emits nothing, so `opsdesk.css` stays the default; those hexes are mirrored in `DEFAULT_NEUTRALS_*` (a test keeps them in step and forbids the hexes anywhere else). Platform console and auth pages never get a tenant brand.

**Contrast (AA).** `brandCss()` also derives the contrast-sensitive brand tokens in `brandTokens()` (hex, via `mixOklab` and `ensureContrast`, which move OKLCH lightness only): `--brand-text` (text colour of the brand, darker in light / lighter in dark), `--brand-deep` (light) and `--brand-3` (dark) text variants, `--on-brand` (white if it reaches 4.6:1 on the fill, else the dark neutral, else black), `--on-bad`, `--hero-from/--hero-to/--hero-patch` (dashboard hero card) and `--promo-btn*` (sidebar promo button). `--brand-soft` is kept light/dark enough for grey and status text on it. A brand whose white-on-fill ratio is 4.0 to 4.6 (the default green was 4.43) has its light FILL nudged just enough (default `#1a8a3a` renders as `#148737`); the stored value is unchanged. The text tokens `--ink-3`/`--placeholder` and the status colours were darkened/lightened to 4.6:1 so tinted neutrals (luminance preserved, tolerance about 1%) stay above 4.5. Rule and test: `ui-rules.md` 11c, `lib/contrast.ts`, `lib/contrast.test.ts`. First paint: the `<style id="od-brand">` is written by the server layout (`app/(app)/layout.tsx`), so it is in the HTML response, not added after hydration.

## Organization logo and favicon (Settings -> Branding)
Two cards under the colour card: **Logo** (PNG, JPEG or WebP, up to 1 MB, 32 to 4096 px a side) and **Favicon** (a square PNG 32 to 512 px, or an ICO of square 16 to 256 px images, up to 256 KB). **SVG is refused everywhere** (script risk). Only settings:write (owner, admin) may change them; everyone in the company sees them.

**API** (`api/src/modules/settings/branding-*.ts`, `image-inspect.ts`). Same B2 file pipeline, no second storage path: `POST /v1/settings/branding/{kind}/uploads` (presigned PUT to the staging key, mime allow-list and size cap per kind) -> `.../uploads/{fileId}/complete` (the policy hook `inspect` reads the staging bytes and checks magic bytes against the declared type, checks the container as far as each format allows (PNG: every chunk length and CRC is verified and nothing may follow IEND; JPEG: the markers up to the frame header are walked and the file must end with EOI, the entropy-coded scan data is not decoded; WebP: the RIFF size must equal the real size and the first chunk must be VP8, VP8L or VP8X, the codec data is not decoded; ICO: the directory entries must be square, inside the file and each a valid PNG or a bitmap header, with nothing after the last image), parses the pixel size from the header, refuses markup or script (`<svg`, `<script`, `<html`, `<iframe`, `<?php`, `javascript:`...) anywhere in the bytes (XMP metadata with `<?xml` is accepted) and a non-square favicon; a refusal deletes the staging object and answers 422 `image_type_mismatch | image_corrupt | image_not_square | image_dimensions | image_suspicious`; no image library) -> ETag-pinned copy and the ClamAV scan -> `GET .../uploads/{fileId}` polls pending/clean/infected -> `PUT /v1/settings/branding/{kind}` `{fileId}` makes a CLEAN upload live (re-reads and re-checks the scanned object, expires the previous file through the existing `file.delete-object` lifecycle, audits `tenant.branding_logo_updated | _favicon_updated` with version, type, size and pixels, never file contents or names) -> `DELETE /v1/settings/branding/{kind}` removes it (`..._removed`, idempotent). Files carry the scoped purposes `branding_logo` / `branding_favicon` (`isScopedPurpose`), so `/v1/files`, search and webhooks never see them; migration **0051** only widens the purpose CHECK. The live state is the `branding` tenant setting (`logo`, `favicon`: file id (never exposed), version = first 16 hex of the scanned SHA-256, type, pixels, bytes). Uploads that were started and never made live are expired (older than 1 hour) whenever that kind is activated or removed. GDPR: a branding file is an ordinary `files` row (owner nulled on erasure, removed with the company).
`GET /v1/settings/branding` answers `{ primaryColor, logo, favicon, storageReady }`; `PUT` of the colour no longer takes a file. At most 5 unfinished uploads per kind per company (429 `too_many_uploads`); abandoned ones older than an hour are expired on every intent. `GET /v1/me/tenant` `brand` carries `logo` and `favicon` (version, type, pixels, bytes) for every member.

**Serving and caching.** `GET /v1/branding/{kind}?v=<version>` (any member of the company, session cookie, no presigned URL): streams the object from storage after checking its stored ETag against the scanned one (a swapped object is a 404), `Content-Type` = the verified type, `Content-Disposition: inline; filename="logo.png"`, `X-Content-Type-Options: nosniff`, `Content-Security-Policy: default-src 'none'; sandbox` (`next.config.ts` leaves `/v1/*` responses' CSP alone, so it reaches the browser), `Vary: Cookie`. `ETag` = the version. A request that names the CURRENT version gets `private, max-age=31536000, immutable` (the web always asks with `?v=` from the session, so a replace changes the URL); any other request gets `private, no-cache` and a 304 on `If-None-Match`. The browser reaches it through the BFF (`/v1/*`, tenant cookie) like every other call.

**Web.** `features/settings/components/brand-asset-card.tsx`: drop or choose, instant preview (object URL), type, size and squareness checked before the upload, progress bar while uploading, "Checking the image", "Scanning for viruses", "Saving", then a Saved chip; short error lines for every refusal (too big, wrong type, not square, extra data, damaged, blocked as infected); Replace; Remove asks first; read-only members see the image and who can change it; **"Storage is not set up"** replaces the upload control when `storageReady` is false (or the API answers 503 `storage_not_configured`). The sidebar mark (`Logo`, `features/shell/components/sidebar-parts.tsx`) shows the uploaded logo in the same 38px box instead of the check mark, followed by the organization name; the collapsed rail shows the logo only; the console keeps the product mark. The company app's tab icon is the uploaded favicon (`app/(app)/layout.tsx` `generateMetadata`, via the memoised session); sign-in, onboarding and the console keep the product favicon (now `public/favicon.ico` set as an explicit root `metadata.icons`, because the file convention cannot be overridden by a nested layout). Skeleton: the Branding tab skeleton has the two cards at the loaded heights (228px at 1568); the sidebar skeleton keeps the 38px mark box either way.

## Audit
`GET /v1/audit` (B7 S7) answers `{ items, nextCursor }`: pages of 100 (`limit` 1 to 100, default 50), newest first in chain order (`seq` desc, so entries with equal timestamps never reorder or repeat). Filters: `entity`, `actorId` (the opaque member id, not a uuid), `action` (exact) or `actionPrefix` (literal; both is 400 `invalid_filter`), `from`, `to` (inclusive; `to` before `from` is 400 `invalid_range`). The cursor is the shared opaque codec (`api/src/core/cursor.ts`, `<at>|<id>`) resolved to its row inside the caller's tenant, so a garbage, forged or other-tenant cursor is 400 `invalid_cursor`. The CSV export takes the same filters (not paged) and records them in its own `audit.exported` entry. Reads never write; the chain is untouched. The web view sends actor, action, record type and dates to the API, follows the cursor with "Load older", and filters only the text search (and "System", which has no actor id) on the loaded rows. The platform console audit (`/v1/platform/audit`) is a separate route and unchanged.

## Users: deactivate and last active (B8 Task 24)

Settings -> Users lists `GET /v1/people?status=all` (settings:read) with the API's **Status** pill (Active / Deactivated) and **Last active** (`lastActiveAt` in tenant wall time; null = "Never"). With settings:write: **Deactivate** asks first (ConfirmDialog) and calls `POST /v1/members/{id}/deactivate`; **Reactivate** is one call (`.../reactivate`, needs a free seat: off when the plan is full). Yourself and the last active owner have the control disabled with the reason as its title; the API refuses too and the refusal is the app's copy (`409 last_owner`, `422 self_deactivation`, `409 already_deactivated | not_deactivated | seat_limit`). The row takes the API's answer at once, then the refresh. The old demo-only columns (`mockActivity`, `getMockUserActivity`, the `settings/users.json` reader) are gone; that seed is read only by the demo seed script now. Devices and Privacy still list the active people only.
